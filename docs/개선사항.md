# 향후 개선사항 정리

## 1) Recency 파이프라인 Kafka 전환
- AS-IS: API 요청마다 `history_places`/`behavior_events`를 받아 즉시 recency 가중치 계산.
- TO-BE:
  1) 이벤트 발생 시 Kafka로 발행
  2) Stream Processor가 실시간 집계 → Redis에 `behavior_summary` 저장
  3) API는 `user_id`로 Redis 조회 후 즉시 적용
- 장점: 요청 payload 감소, 계산 비용 분리, 지연/부하 관리 용이

## 2) behavior_summary 스키마(예시)
- key: `user_summary:{user_id}`
- value: `items[]`
  - `place_id`
  - `category`
  - `weight` (시간감쇠/이벤트 가중치 반영된 최종값)
  - `last_occurred_at` (옵션)
- 음수 weight 허용: dislike/hide/skip 등 부정 신호 반영

## 2-1) 상세 행동 이벤트 활용 규칙
- 입력은 정해진 타입(enum)만 허용하고, 정규화는 하지 않음
- 사용 데이터(필수)
  - `user_id`, `place_id`, `category`, `event_type`, `occurred_at`
- 타입별 추가 데이터
  - `dwell` 이벤트는 `dwell_seconds` 필수
- 허용 이벤트 타입
  - `view`, `click`, `like`, `bookmark`, `dwell`, `hide`, `dislike`, `skip`
- 기본 가중치
  - `click`, `view`, `like`, `bookmark`는 양수 가중치
  - `hide`, `dislike`, `skip`은 음수 가중치
  - 가중치 크기는 환경변수(`BEHAVIOR_WEIGHT_*`)로 조정
- 체류 시간(dwell)
  - `dwell_seconds < BEHAVIOR_DWELL_MIN_SECONDS`면 0 처리
  - 로그 스케일로 변환 후 `BEHAVIOR_DWELL_MIN_WEIGHT~MAX_WEIGHT` 범위로 매핑
- 시간 감쇠
  - `occurred_at` 기준 지수 감쇠를 곱해 최신 행동일수록 더 큰 영향
- 집계 방식
  - `(user_id, place_id, category)` 기준으로 누적 합산
  - `last_occurred_at`는 최신 이벤트로 갱신
  - 운영 안정화를 위해 top-N 유지/가중치 클리핑 옵션을 권장

## 3) API 변경 방향
- `behavior_events` 기본 제거, `user_id` 기반 조회로 전환
- 필요 시 일부 direct 이벤트만 허용(실시간 우선 케이스)
- `history_places`는 방문 이력 제외 및 fallback용으로 유지

## 4) Recency 점수 구조는 유지
- recency 벡터 = Σ(weight_i * item_embedding_i) → 정규화
- `score_recent = recent_weight * (item_embedding · recency_vec)`
- 최종 점수: `base + distance + recency + popularity` 구조 유지

## 5) Negative / Not-seen 처리
- 안 본 데이터: summary에 없음 → 영향 0
- 싫어요/숨김: weight 음수로 누적 → 점수 감점

## 6) 성능/운영 포인트
- Kafka lag 모니터링 (summary 반영 지연)
- Redis TTL/유실 대비 fallback(기본 추천 유지)
- summary 크기 제한(top-N, 최근 T일)
- 집계 idempotency/중복 처리

## 7) 환경변수(추가 예정)
- `KAFKA_BOOTSTRAP_SERVERS`
- `REDIS_URL`
- `SUMMARY_TTL_DAYS`
- (옵션) summary top-N 제한값
